Migrations use drizzle's node-postgres migrator and are tracked in `drizzle.__drizzle_migrations`, so re-running is a no-op. Logs print only RUN/SKIP, the reason, the count and the `ep-…` endpoint id; errors are scrubbed of URLs and credentials. Then `scripts/vercel-seed.ts` seeds the synthetic demo users, **preview only**. It is idempotent and never resets an existing password (that needs `pnpm seed:demo-users --apply --reset-passwords`, run by hand). It skips with a logged reason if the URL is missing (the demo accounts need no password env var: DECISION-LEDGER row 59, and drizzle/0005_demo_shared_password.sql sets their hash on production as part of the migrate step). Production is never seeded from the build; the demo reset/seed buttons are B-15 (row 17).

## Migrations in repo
**Frozen:** a migration is frozen once it has been applied to any shared Neon branch. 0000 and 0001 were applied to previews and production on 2026-10-14; 0002 and 0003 followed (production build of main @ b1df48c), so 0000–0003 are all frozen. Never edit a frozen file: fix forward with a new migration — 0008 is the worked example, carrying two corrections to 0007 rather than editing it.

**No manual Neon snapshot is required before migrations while the database holds only demo data; Neon's built-in restore window is the fallback. Revisit before real data arrives.** (Decided by founder, 2026-10-16 10:24 ET — DECISION-LEDGER #66, superseding the standing snapshot step of #43.) A written rollback is still owed by every prod-migrating merge: the Rollback column below is the schema-only answer, and it cannot bring back data a migration changed or dropped. The prod-release-gate (`MIGRATE_PROD_ON_BUILD=1` on `main`) is what makes that moment identifiable in advance. Nothing in CI runs a rollback file; they are reference, and none of them has been run.

**The fallback, and its limit: Neon's restore window is 6 hours.** Point-in-time restore on the Free plan reaches back 6 hours only. That is the whole safety net now, and it is a window rather than a point: a bad migration has to be noticed inside 6 hours for a restore to reach past it. The bar is acceptable because the one database holds synthetic demo data only (ADR-000 #4/#6, DECISION-LEDGER #17) — there is nothing in it whose loss is not a reseed. **Revisit before real data arrives**, which is also when the restore drill below stops being optional.

The last manual snapshot, `pre-0008-2026-10-15` (taken by the founder at 9:54 AM ET on 2026-10-15 with 0007 applied, no expiry), still exists and is still a way back to that state. It is no longer retaken before each migrating merge, and nothing is sequenced behind taking one. Note the Free plan allows exactly **one** manual snapshot with no history, so taking another replaces this one — if a future migration does want a restore point, record the new name here when it replaces this one.

There is no 0004: the thread uniqueness index was renumbered to 0006 to sit behind main's 0005 (commit 1e10495), and the gap is left as it is because a migration file's number is its identity in `drizzle.__drizzle_migrations`.
