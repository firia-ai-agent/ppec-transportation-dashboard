0. What changed vs the three source PRDs (one-paragraph digest)
AWS-hosted TypeScript modular monolith, PostgreSQL, pg-boss behind a JobScheduler seam, transactional outbox, SSE. Amazon Location on every routing call that touches real or realistic coordinates (Google only in a sealed benchmark project). Claude via Bedrock (or Anthropic HIPAA-ready org) behind a token-only LLM gateway. Twilio 1:1 SMS on a 10DLC number registered under the center's legal entity; Group MMS is optional and never core; Conversation Orchestrator never enabled. Teams via the M365 Agents SDK, links/tokens only, no dependence on RSC. Traccar on an authorized adult's phone + mandatory GPX replay for P1; OBD/telematics in P2. D3's layout-based capacity solver merged with D1's per-stop sequencing and D2's "present ≠ functional." Tokenization-at-ingest from P1 (D3) with D1's interface list and no name/DOB fallback matching. P1 ≈ 109 ideal engineer-days (range 81–146); base-case first-year cash ROI is negative on a single center; the case is safety, coordinator capacity, and removal of the single point of failure.

1. Product definition
Outcome. Whenever a parent, provider, therapist, or staff member sends a message, or a timer, GPS point, or traffic shift occurs, the system resolves the exact child/family/leg, validates permission and safety constraints, updates authoritative operational state, revises the plan where authorized, updates the coordinator dashboard, notifies only the affected parties, and tracks every unresolved item with durable timers until verified completion. (D1 §1.2 G1–G5; D2 "five questions"; D3 §1.1.)


Not an EHR, billing system, staffing scheduler, or chatbot. Clinical charting, diagnoses, claims, and medication stay in the client's systems (D1 §1.4; D2 scope; D3 §1.4).


Epistemic vocabulary on every operational fact: SCHEDULED (intent) → REPORTED (someone said) → VERIFIED (authoritative party or sensor confirmed) → COMPLETED (custody/terminal event recorded); GPS is OBSERVED evidence of a device, never of a child (D1 §5.2; D2 state classes; D3 §4.1).

7. Capacity solver (deterministic; no LLM)
Vehicle v has layouts L(v) (mutually exclusive, e.g. {0WC/6A}, {1WC/3A}, {2WC/1A}). Each layout ℓ: wheelchair positions W_ℓ (each with securement type sec(w) and max footprint len_w × wid_w), ambulatory seats A_ℓ, tether/LATCH-capable seats T_ℓ ⊆ A_ℓ, lift_required(ℓ). Daily inputs: lift_ok(v), unavail(v) (malfunctioning positions/seats). Child c: mobility ∈ {AMB, WC}, measured len_c × wid_c, sec(c), tether(c), escort(c), child-owned equipment dims. On_k = set onboard after stop k (per manifest stop sequence).


Feasible(v, leg) ⇔ ∃ ℓ ∈ L(v) such that ∀ k:


1. an injective f: WC(On_k) → W_ℓ \ unavail with sec(f(c)) = sec(c), len_c ≤ len_f(c), wid_c ≤ wid_f(c);
2. #AMB(On_k) + Σ escort(c) + staff_escort_k ≤ |A_ℓ \ unavail|;
3. #tether(On_k) ≤ |T_ℓ \ unavail|;
4. (WC(On_k) ≠ ∅ ∧ lift_required(ℓ)) ⇒ lift_ok(v).


Layout fixed per leg (ASM-17). Unknown capability → CAPABILITY_PENDING, never assumed feasible. Implemented as bipartite matching per k over ≤4 layouts. Output: feasible layout, or deficit {k, type, count} and ranked options (split run, alternate vehicle/provider, family transport, delay, cancel) — human approves. Tests: 2-seat crisis {1WC,2AMB} vs {1WC,1AMB} → INFEASIBLE deficit 1 AMB; substitution → UNKNOWN → re-request → re-solve; no feasible vehicle → RED, no auto-assignment; infeasible at stop 3 → report k=3, never propose unloading a boarded child.

16. Phase 3: scale and degraded modes
* Scale drivers: concurrent legs, vehicles with telemetry (positions/min), recalcs/min, message bursts (weather day; bounded by 10DLC MPS), users, retention, human exception load. Monolith handles hundreds of concurrent legs; revisit partitioning beyond ~5,000 daily legs or multi-tenant.

* SLOs: console availability 99.5% operating hours; routine message→action p95 <60 s; delay notice p90 <10 min from threshold; expansion gate = 8 weeks on SLO, zero wrong-recipient, positive staff review.
* Degraded modes: LLM down → keyword parser (ABSENT/SICK/YES/READY/STOP) + inbox triage banner; SMS down → click-to-call sheet, manual ack logging; stale GPS → freeze ETA texts, driver/dispatcher prompt, manual status; EHR failure → last good data + stale banner, CSV fallback; Teams down → SURF-05 authoritative; routing down → historical durations flagged as estimates, "running late, update to follow" only after staff approval. On-duty coordinator runs the runbook; platform owner fixes the adapter.
* Deferred to P3: existing-platform adapter (if feasible), provider telematics adapters, provider portal, check-in bidirectional sync, staffing insight report, payment analytics (read-only, after rules documented), EHR write-back (only if vendor API), parent web status page (only if SMS insufficient), multilingual templates (P3 unless CA-15 says otherwise), on-call/runbooks/training.

17.4 Baseline and pilot design
4-week baseline (2-week time-and-motion tally sample, message/call logs, therapist cancellations, provider invoices, EOD items; weekly seasonality captured) → 2-week shadow → 6-week pilot (routes 1–2 weeks 1–3, all routes after). Pre/post same weekdays; stepped rollout as partial control; normalize per 100 legs; stratify by provider and weekday; record confounders weekly (census, provider changes, illness, turnover, holidays) and exclude anomalous weeks by pre-declared rule. Sufficiency: ≥150 comparable changes per period; ≥8 weeks for monthly metrics. Go/no-go (ASM-25, FQ-06 to confirm): veto = any wrong-recipient PHI disclosure or custody error. Pass = notification p90 ≤15 min and ≥95% of affected parties delivered within 5 min (1:1 receipts), coverage ≥98%, mismatch-at-arrival −50% or zero, coordinator minutes/change −25%, ETA p80 error ≤7 min, staff satisfaction ≥ neutral.
