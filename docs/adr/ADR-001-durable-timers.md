# ADR-001 Durable timers and workers on Vercel + Neon
**Status: Proposed** (Firia, 2026-10-14). Needs Rudy's spike + TEST-INF-01 pass before Accepted. Delay granularity settled by DECISION-LEDGER row 60 (whole-second queue delays + inline lease re-check); all timings below are **simulated**, pending Firia's restart drill and the live delay probe.
**Context.** PRD NFR-03: timers survive restarts and fire within 5 s of due. Cron on Pro is 1-minute granularity, so cron alone cannot meet 5 s.
**Decision.** `ops.job` row is the source of truth (written in the same transaction as the domain change). On insert, publish a Vercel Queues message with `delaySeconds = ceil(due - now)` in **whole seconds** (row 60), idempotency key = job id, and the row's `(dueAt, version)` as a **fence**. Consumer does a guarded claim in **one transaction** (`claimForWake`): `SELECT … FOR UPDATE`, refuse with a named reason if the job is cancelled, already DONE, DEAD, already CLAIMED, fenced out as superseded, or more than 1 s early, else `UPDATE ops.job SET state='CLAIMED', claimed_at=now(), claimed_by=$token, claimed_until=now()+2s`; every refusal is a no-op + **ack**, never a throw, because on an at-least-once unordered queue with no delay SLA all of them are expected traffic — bar one: a *first* wake that is more than `EARLY_SLACK_MS` = 1 s early never reaches the claim, because `handleWake` re-publishes it for the remaining wait + 250 ms, rounded up to a whole second (`deferEarlyWake`). Acking it would throw the job's only wake-up away: `arm` has already set `wake_published_at`, so the sweep's re-arm pass skips the row and only the overdue pass (> 5 s past due, 60 s cron) would fire it. A failed re-publish clears `wake_published_at` so the next sweep re-arms. The row lock spans the check and the claim, so two concurrent duplicate deliveries resolve to exactly one winner. The fence is `(due_at, version)` and deliberately **not** `version` equality: `reschedule` moves `due_at` and bumps `version` together (so a differing `dueAt` means the wrong generation and is dropped), while `reclaimIfExpired`/`markFailed` bump `version` and leave `due_at` alone (so a version merely *behind* the row is a legitimate retry of the same firing and must pass — an equality fence would disable Option A). **Option A, retuned (DECISION-LEDGER row 58 "Accepted by default (Firia, within founder locks)", Firia → Rudy relay 2026-10-14 14:22 ET, superseding the 3 s lease proposed for row 38 — PR #10 was closed unmerged, and row 38 reached the ledger via main, so row 58 supersedes its parameters rather than editing it) and made delay-granularity-independent by DECISION-LEDGER row 60:** the lease is **2 s**; at claim time the consumer publishes a re-wake delayed 2 s; a re-wake or redelivery that finds an expired lease (`claimed_until <= now`) reclaims it and fires through the same claim; one that finds the lease **still live** no longer no-ops and drops recovery onto the 1-minute sweep (Veri review of PR #10, blocker 1) — it waits the rest of the lease out. **Every published `delaySeconds` is a non-negative whole number of seconds** (`wholeSecondDelay`, rounded **up** — a delay is a "not before" floor, so rounding down would ask for a delivery before the thing we are waiting for), because @vercel/queue 0.8.0 types the field `delaySeconds?: number` and forwards it verbatim as the `Vqs-Delay-Seconds` header, but the Queues docs describe it only as "Delay in seconds" and promise **no sub-second precision anywhere**; row 58's millisecond re-wake delays rested on undocumented behaviour of a Beta service, and row 60 takes that dependency off the critical path. Both transports check the invariant: the production one rounds up and logs (a published wake beats a strict error), the fake one in tests throws, so a regression fails CI. What replaces the sub-second hop is an **inline lease re-check** (`recheckLeaseInline`): a wake that finds a live lease with at most `INLINE_RECHECK_MAX_MS` = lease + claim slack = **3 s** left sleeps to `claimed_until` + 250 ms *inside the same invocation*, re-reads the row, and reclaims + fires there — no second queue hop, so no second helping of delivery jitter and no whole second spent covering 1 ms of leftover lease. The bound is deliberately the **whole lease plus the claim slack**, so every lease a dead consumer can leave behind is recovered in one invocation; it is bounded twice (≤ 3 s per pass, ≤ 3 passes, so ≤ 9.75 s against the consumer's 60 s `maxDuration`) and it **writes nothing**, so the fencing is untouched: the reclaim still needs `state='CLAIMED' AND claimed_until <= now`, the fire still needs `SCHEDULED`, and `claimed_by` still carries the per-claim token that fences the DONE update. Only two cases still publish a re-wake (whole-second, ≥ 1 s): a lease longer than the bound — one a live handler is renewing, where the job is not at risk — and a re-check that runs out of passes. A handler that outlives the lease **renews** `claimed_until` every LEASE/2 = 1 s on its own connection, fenced by the claim token, and abandons its commit if the renewal shows the claim gone; a failed handler throws and Queues redelivers with **bounded exponential backoff** (2 s, 4 s, … capped at 60 s) instead of at once. Simulated kill-after-claim lateness (jobs.test.ts, 14 runs, jitter ≤1 s per delivery and early arrival ≤1 s, **all SIMULATED — fake clock, in-memory transport, PGlite; nothing measured live**): the analytic bound is `lateness = (ceil(due−now) − (due−now)) + j₁ + lease + (j₂ at expiry | 250 ms margin inline)`, i.e. **< 5.0 s** at expiry and **< 4.25 s** inline, both suprema (the rounding term is < 1 s and never equals it); the worst value in the table is **4.95 s** (rounding 0.95 s, j₁ = j₂ = 1 s) and the early-arrival path — the one that was over the bar before — is **4.20 s** at the same rounding. When the due time lands on a whole second, so our rounding costs nothing, the two paths are **4.00 s** and **3.25 s**, which is the like-for-like comparison with row 58's 4.25 s. Read that honestly: the recovery mechanism itself costs lease + margin = **2.25 s**, and the rest of the budget is our own whole-second rounding of the *schedule-time* wake plus two doses of an **assumed** 1 s per-delivery jitter, so the at-expiry path has ~0.05 s of margin in the worst corner of the model. Two knobs if the live run wants more of it: the probe may show real jitter far under 1 s (then the bound collapses towards 2.25 s), and the rounding term can be removed outright by publishing the schedule-time wake with `floor` and waiting out the sub-second remainder with the same inline trick — not done here, because it would hold an invocation open on *every* timer, not just the recovery path. Neither is needed for NFR-03 to be met inside this model; both are reported so Firia and Veri can choose. Every-minute cron sweeper: fires overdue SCHEDULED jobs, reclaims CLAIMED past `claimed_until`, re-publishes jobs due in the next 7 days with no live message, and marks `DEAD` after 5 attempts (creating a RED task). Each deployment's first sweep writes `runtime_marker.active_deployment_id` and re-arms because queue messages are pinned to the publishing deployment. Queue-side tuning uses the only three knobs @vercel/queue 0.8.0 exposes: `retryAfterSeconds: 2` on the trigger (the lease, not the 60 s default), `visibilityTimeoutSeconds: 30` — the package's documented **floor**, so it cannot match the 2 s lease, which is precisely why Option A recovers through our own re-wake rather than through queue redelivery — and a `retry` callback that backs off 2 s → 60 s then acknowledges at 8 deliveries, standing in for the **`maxDeliveries` option and DLQ the package does not have**. All behind `JobScheduler` (schedule/cancel/reschedule) so AWS swaps to pg-boss on Fargate.
**Alternatives.** Cron only (fails 5 s). pg-boss in Vercel functions (needs a long-lived worker; no host for it in P1). Inngest / QStash (another vendor + BAA later; fine technically). Vercel Workflow `sleep` as the store (state lives outside our DB; harder AWS exit). 
**Consequences.** Queues is Beta: if it fails TEST-INF-01, fallback is the sweeper at 1-minute granularity plus a documented NFR-03 deviation (founder decision) or QStash behind the same seam. Recovery no longer depends on Queues' delay *granularity* (row 60) — only on its delay *lateness*, which no SLA bounds and which the simulation assumes is ≤1 s per delivery. So **PPE-43 / NFR-03 stays UNVERIFIED**: the 4.95 s worst case above is **simulated**, not measured, and the live TEST-INF-01 run on the synthetic prod deployment (row 18) is still owed — the restart drill (Neon compute restart of `main`, to be triggered by Firia) **and** the delay probe (`GET /api/probe/delay`), whose job is now to measure the real jitter distribution and tell us how much precision whole-second delays leave on the table, not to decide whether the design holds. If the measured jitter is materially worse than 1 s per delivery, the knobs are (in order): floor the schedule-time delay and wait the remainder out inline (−1 s from the bound), shorten the lease, widen the margin. The recovery parameters (lease, re-wake margin, inline re-check bound) remain the knobs. **Queues delivery contract (Athena, PR #21).** At-least-once, **unordered**, **no delay SLA** (`delaySeconds` is a "not before" floor), default redelivery 60 s, deployment-pinned, no DLQ. So the transport is an alarm clock only: correctness is the guarded claim plus the fence, and the 4.95 s worst case is a *tuning* claim, simulated, that the live run has to confirm. The docs' silence on sub-second `delaySeconds` is what row 60 acts on: delays are whole seconds and the sub-second part of a lease is waited out in-invocation. `scripts/test-inf-01/delay-accuracy.ts` (**PROPOSED, not run** — needs a preview deployment and Firia's go-ahead) measures the distribution over 300 probes.
